I have read the PDF you uploaded, Rahnuma 1.3.0, not just the excerpt. It is 114 pages, dated 3 October 2026. The sharing architecture needs to be corrected to reflect what the document actually establishes.

The most important correction is this:

> The platform is not merely a content site with social sharing. It is a graph of work, repositories, evidence, provenance, collaborators, domains, languages, projects and contribution paths. Sharing must expose that graph without flattening it.



Rahnuma explicitly describes the estate as a typed graph, and warns that adjacency, dependency, projection, composition and temporal sequence must not be conflated.  It also defines the cultural projections as parallel traversals rather than a hierarchy. 

So the specification to Grok should be revised accordingly.

Build Specification for Grok

Information Sharing and Cross-Ecosystem Discovery

Critical scope restriction

This component is for sharing information only.

It is not:

- a social network
- a follower system
- a centralized social graph
- an automated publishing system
- a political communication system
- an advertising system
- a user-tracking system
- a centralized analytics database
- a substitute for Git/GitHub collaboration
- a mechanism for automatically transmitting project files
- a mechanism for automatically exposing private project state

The user must explicitly initiate the share.

The platform may detect, prepare and suggest a share, but it must never publish automatically.

39. Exact instruction to Grok

Add this to the build contract:

> Implement sharing as an information-projection subsystem over the canonical ecosystem graph. Do not implement it as a collection of social-media buttons. Every meaningful public artifact must be shareable, but sharing must preserve the artifact's identity, version, evidence state, provenance and graph relationships. The system must distinguish information sharing from persistence, contribution, collaboration and publication. All generated messages must originate from configuration. The ShareEngine must discover relevant graph-linked information and construct a context-appropriate projection for the selected audience and channel. It must never flatten typed relationships into generic "related content", never silently publish, never transmit the complete local project, never expose private project data, and never infer evidence stronger than the canonical evidence state. GitHub Issues may be used as a persistence mechanism because the static platform has no database, but GitHub semantics must remain an adapter rather than the platform ontology.



And add these acceptance criteria:

[PASS] Every public artifact has a Share action
[PASS] Share action resolves canonical identity
[PASS] Share action resolves canonical URL
[PASS] Share action resolves version
[PASS] Share action resolves evidence state
[PASS] Share action resolves provenance
[PASS] Share action traverses typed graph relations
[PASS] Share action selects only public information
[PASS] Share action never serializes entire local project
[PASS] Share message comes from configuration
[PASS] Channel-specific template comes from configuration
[PASS] Language/script selection is explicit
[PASS] Evidence terminology is preserved
[PASS] DOI/citation can be shared when available
[PASS] Repository can be shared when available
[PASS] Contribution path can be shared when available
[PASS] Roadmap/issue path can be shared when available
[PASS] Related ecosystem links are bidirectionally discoverable
[PASS] Preview shows exact information boundary
[PASS] Publication requires explicit user action
[PASS] No central social database exists
[PASS] GitHub persistence is an adapter
[PASS] Share history can operate locally
[PASS] Adding a new artifact implementing Shareable automatically exposes sharing

This is the correlation I would use going forward. Rahnuma should be treated as an architectural source for the sharing system itself, especially its typed graph, provenance/evidence discipline, repository/DOI model, GitHub issue workflow, collaborator lanes, language/script separation, and the guide -> issue -> contribution -> verification -> publication loop.
